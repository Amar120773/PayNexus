# Temporal Signals Zero Diagnosis

## 1. Symptom
The PayNexus Merchant Investigation UI was displaying exactly `0.0000` for all Temporal Signals (e.g., Refund Rate Change, Network Growth, Device Churn, IP Churn) across all merchants investigated (M00109, M00150, M00001).

## 2. Dataset Analysis
Inspection of the frozen V2 dataset (`data/synthetic_v2/evolution_features.csv`) containing 5000 rows confirmed that temporal features are **not exclusively zero**. For example:
- `volume_delta_t1_t2`: Only 12.28% zeros
- `device_churn_t1_t2`: 72.90% zeros (meaning >27% non-zero values exist)
- True values for merchant M00109 included `volume_delta_t2_t3 = -2607.63`, `device_churn_t2_t3 = 0.666`, etc.

## 3. Raw Temporal Data Analysis
The raw temporal data (`transactions.csv`, `relationships.csv`) absolutely contains temporal evolution. The `timestamp` ranges from `2026-01-01` to `2026-03-31`. Relationship evolution and event boundaries precisely match this 2026 timeframe.

## 4. Feature Generation Analysis
The API endpoint (`POST /v1/score/merchant`) uses `src.features_v2.evolution_features.extract_evolution_features` to dynamically extract point-in-time features to prevent label leakage. This function uses strict 30-day time windows backward from the provided `scoring_timestamp`:
- T3: `scoring_ts`
- T2: `scoring_ts - 30 days`
- T1: `scoring_ts - 60 days`
- T0: `scoring_ts - 90 days`
If there are no events in these windows, the structural and behavioral aggregations correctly evaluate to `0.0`.

## 5. API Analysis
When querying the API manually with the default frontend payload:
`{ "merchant_id": "M00109", "scoring_timestamp": "2024-03-31 00:00:00" }`
The API responded with probability `0.00683` (LOW RISK) and temporal features exactly `0.0`.
When querying the API with the correct 2026 timestamp:
`{ "merchant_id": "M00109", "scoring_timestamp": "2026-03-31 00:00:00" }`
The API correctly responded with probability `0.9824` (HIGH RISK) and temporal features perfectly matched the non-zero dataset facts (`volume_delta_t2_t3 = -2607.63`).

## 6. Frontend Mapping Analysis
The frontend correctly maps `evidence_features` directly from the API response into the UI. The root defect was not in the mapping logic itself, but in the **request payload variables**.
The `merchant/[merchantId]/page.tsx` file hardcoded the initial investigation timestamp and timeline history array strictly to `2024` instead of `2026`.

## 7. Root Cause
**F. Scoring timestamp/history-window issue.**
The V2 dataset represents events between `2026-01-01` and `2026-03-31`. Because the frontend requested the point-in-time score on `2024-03-31`, the time windows generated by the feature extractor reached backwards into late 2023 / early 2024. The dataset naturally contained no transactions for those 2024 windows, causing every temporal feature delta and growth metric to evaluate to exactly `0.0`. 

## 8. Fix Applied
This was a purely frontend defect. The fix was applied cleanly in `dashboard/src/app/merchant/[merchantId]/page.tsx`:
- Replaced the initial `selectedTimestamp` default from `"2024-03-31 00:00:00"` to `"2026-03-31 00:00:00"`.
- Replaced the hardcoded `timelineTimestamps` array replacing all `2024` years with `2026`.
